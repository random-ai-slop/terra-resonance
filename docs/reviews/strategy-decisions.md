# Product sufficiency: lead synthesis awaiting counterreview

Historical synthesis of STRATEGY, ROADMAP and three roadmap studies. Task assumptions came from user goals and public examples, not human interviews or validated user research.

These improve the first complete delivery rather than postponing small high-value tasks. An internal slice may begin with three questions, but all six and all promised formats remain final requirements. The later counterreview reduced mandatory points to one and removed redundant aspect/quality fields; this table preserves the proposal as written at the time.

## Explicitly excluded from that baseline

- Dual viewports: common-l/m spherical angular bases make curves/tables, selected radius and rapid same-camera switching the priority. Add dual views only when a concrete localization/mixed-shape comparison needs them; not a permanent exclusion.
- Native multiscene timelines, automatic lessons/narration and arbitrary camera animation: first deliver stable scenes and portable assets, then respond to repeated composition tasks.
- Mature kernels/inversion: start with finite differences and experimental Q evidence, then validate each kernel's integral relationship; attractive kernel plots are not inversion capability.
- Real sources/observations: high-value near-term work with independently checked source/instrument/unit chains, not manual coefficients masquerading as excitation. Baseline probes retain explicit meaning.
- Advanced physics/platforms: keep research stages but no unusable rotation/rheology switches, marketplace or cloud-job system.

## Longer-term choices

1. A completes science, explanation and production together rather than leaving mutual debts between releases.
2. B develops material/interface sensitivity and external cross-checks in parallel; a second backend may enable earlier radial anisotropy.
3. C source → receiver → observation validates each observable's units/operators and independent synthesis.
4. D studies slow rotation/ellipticity/weak nonspherical coupling; E chooses a bounded complex-rheology, direct-3D or inversion branch rather than promising all.
5. Teaching, production, performance and maintenance span every stage without waiting for advanced physics.
6. Stabilize meaning, identities and a few APIs now. Abstract adapters/large-array containers only after a second concrete implementation; represent new physics explicitly rather than burying it in universal metadata.

## Questions for counterreview

Which core task becomes materially worse if an addition is removed? If none can be named, remove or postpone it. Does reuse hide substantial numerical/output complexity? Do deferred features block the actual user goal, and are their reasons valid? Do long dependency chains unnecessarily block high-value small work? Are current modules/data sufficient without speculative ambiguity? What evidence marks the transition from planning to implementation?
